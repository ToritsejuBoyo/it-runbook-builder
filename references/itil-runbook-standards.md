# Enterprise ITIL & SOC 2 Runbook Standards Reference

## 1. Governance & Compliance Framework

Enterprise Standard Operating Procedures (SOPs) and technical runbooks serve as foundational audit artifacts for ISO/IEC 20000, SOC 2 Type II (Change Management Principle CC6.8), and ITIL v4 Continual Service Improvement.

To satisfy enterprise compliance mandates, every operational runbook generated by `it-runbook-builder` must enforce eight immutable structural pillars:

| Pillar | Governance Requirement | Operational Objective |
| :--- | :--- | :--- |
| **1. Metadata & Lifecycle** | Document ID, Owner, Review Cycle, Target Scope | Prevents undocumented tribal knowledge and establishes accountability. |
| **2. Access & Prerequisites** | Least privilege RBAC roles, network ports, tools | Enforces access boundaries and eliminates ad-hoc permission guessing. |
| **3. Pre-Flight Checks** | Read-only assertions of initial system state | Verifies baseline health before mutating state, preventing cascading failures. |
| **4. Parameterized Steps** | Copy-paste commands with `<VARIABLE>` tokens | Eliminates hardcoded environment risks and ensures staging/prod portability. |
| **5. Step Verifications** | Explicit paired check for each state change | Immediately catches partial execution failures before downstream damage occurs. |
| **6. Mandatory Rollback** | Step-by-step reversal sequence | Guarantees deterministic backout paths when unexpected anomalies arise. |
| **7. Common Failures** | Symptom-cause-remediation matrix | Empowers frontline L1/L2 engineers to triage blockers independently. |
| **8. Audit & Cleanup** | Artifact cleanup, log rotation, ticket closure | Preserves clean disk footprints and closes audit trail loops. |

## 2. Command Parameterization Standards

Hardcoded values create catastrophic blast radius risks when a junior engineer executes a command intended for staging against production. All command sequences must be parameterized according to the standard dictionary:

| Token Placeholder | Description | Example Target |
| :--- | :--- | :--- |
| `<TARGET_HOST>` / `<TARGET_FQDN>` | Target machine hostname or public domain | `api.corp.internal` -> `<TARGET_FQDN>` |
| `<TARGET_IP>` | IPv4 or IPv6 network address | `10.240.1.50` -> `<TARGET_IP>` |
| `<SERVICE_NAME>` | Systemd, Windows Service, or Daemon | `nginx.service` -> `<SERVICE_NAME>` |
| `<PORT>` | Target listening TCP/UDP port | `8443` -> `<PORT>` |
| `<DEPLOYMENT_NAME>` | Kubernetes Deployment or DaemonSet | `payment-api` -> `<DEPLOYMENT_NAME>` |
| `<BACKUP_PATH>` | Path to pre-change backup archive | `/etc/app/config.bak` -> `<BACKUP_PATH>` |
| `<SECRET_TOKEN>` | Bearer or API authentication token | Automatically masked by `--sanitize` |

## 3. Pre-Flight Check Best Practices

Pre-flight checks must be strictly read-only:
1. **Never alter state during pre-flight:** Do not execute `systemctl restart`, `rm`, or `set` commands.
2. **Verify port availability:** Check if listening sockets are healthy before starting new daemons (`ss -tlpn`, `netstat -ano`).
3. **Verify disk headroom:** Confirm root and target data volumes have $>20\%$ available capacity (`df -h`).
4. **Inspect DNS resolution:** Ensure name resolution responds with expected records (`dig +short`, `Test-NetConnection`).

---

## 4. Rollback & Backout Engineering

A backout plan is only valid if it reverses changes in **reverse chronological order**:
- If Step 1 backed up a configuration file and Step 2 modified it, Rollback Step 1 must restore the backup and Rollback Step 2 must reload the service.
- If a database migration was executed, the rollback must invoke the corresponding down-migration script or restore the snapshot taken in Pre-flight.
